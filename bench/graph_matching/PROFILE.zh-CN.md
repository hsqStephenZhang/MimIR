# MimIR 与 portmatching：搜索开销排查

2026-11-02。结论仅针对已有 benchmark 中的当前实现，没有修改生产匹配器，也没有推进之前的模式表示优化。

**共同端口 DAG 测试主要慢在预过滤缓存、候选集合处理和 continuation 的堆分配；原生单根长链主要慢在结果读取集合的重复遍历。** 两类工作负载的瓶颈不同。测量没有执行 RewritePlan、World 重建或发布，也没有使用依赖类型约束，因此这些机制不是这组搜索时间的来源。

## 证据与测量边界

使用之前的 Release 二进制、相同输入、CPU 2。先对未插桩的 MimIR 和 portmatching naive 运行 `perf record`，再把 `match.cpp` 复制到临时目录，构建单独的 `LD_PRELOAD` 诊断库，记录互斥阶段耗时、访问次数和分配量。Rust 只在 `find_matches().collect()` 周围打开分配计数。

四个输入（chain/shared-dag/wrong-port/many-chain，128 个组件），每个配置重复 7 次。诊断副本和两种剥离实验的**完整有序节点映射集合**均与原始结果相同，所有搜索 Complete。生产 `match.cpp` 的 SHA-256 与前一轮 benchmark 记录一致。

插桩会扰动时间：七模式链原始搜索中位数为 **103.95 ms**，诊断版本为 **113.98 ms**，增加约 9.7%。下面阶段时间来自诊断版本，不能当成原始二进制的精确分摊。阶段分别取中位数，其总和不保证恰好等于总时间中位数。分配字节是累计申请的 payload，不是峰值内存或 RSS；结果解码、文件输出、oracle、返回结果的最终析构均不在搜索计数中。

## 七模式链：时间花在哪里

目标图有 1536 个逻辑顶点；MimIR 适配后为 **6019 个物理节点、2944 个 operation**。七个模式返回 7168 个结果，只尝试了 32256 个根候选，说明此例的差距不能归因于枚举所有根组合。

| 阶段 | 中位数 ms | 约占比 | 分配次数 | 累计申请 MB |
| --- | ---: | ---: | ---: | ---: |
| 递归结构预过滤 | 35.31 | 31% | 363465 | 21.31 |
| 动态候选收缩 `narrow` | 33.31 | 29% | 1472169 | 133.08 |
| 根枚举、结构解释与 continuation | 26.36 | 23% | 752664 | 36.13 |
| 构造匹配结果及读取集合 | 8.93 | 8% | 214992 | 34.84 |
| 搜索临时状态清理 | 8.82 | 8% | 0 | 0 |
| 连通性/捕获分析及初始索引准备 | 0.46 | <1% | 1513 | 2.82 |

MimIR 搜索总计 **2804803 次分配、228.19 MB**。同输入 portmatching naive 为 **378484 次、28.57 MB**，分别相差约 **7.4 倍、8.0 倍**。Rust 诊断版本搜索约 8.66 ms；之前未插桩版本约 7.52 ms。portmatching 本身也有绑定 HashMap、临时 Vec 和去重开销，区别在于总工作量和分配量明显更小。

### 1. 预过滤缓存保存了大量比直接检查更贵的状态

[match.cpp](../../src/mim/pattern/match.cpp#L325) 用 `std::map<(pattern_id, Def*), bool>` 缓存递归结构检查。七模式链进行 635264 次缓存查询，保存 363041 个状态，命中率约 **42.9%**。每个新状态涉及红黑树查找、节点分配、插入，搜索结束还要逐个释放。很多检查本身只是 kind/arity/指针相等比较。

未插桩的 `perf` 中，递归 `may_match` 分发函数本身是最大的单项热点，约占 core cycles 的 24%；分配器及红黑树操作另外计数。

为验证因果，临时副本只禁用这一张缓存，**保留 Indexed 模式的候选索引、MRV 和全部检查**：

| 诊断配置 | 七模式链搜索 ms | 端口错误反例搜索 ms |
| --- | ---: | ---: |
| 完整诊断版本 | 113.98 | 1.510 |
| 仅不使用预过滤缓存 | 76.64 | 0.161 |

不缓存时七模式链实际执行的预过滤调用从 635264 次增加到 1443456 次，但该阶段从 35.31 ms 降到约 6.23 ms，临时状态清理也从 8.82 ms 降到约 2.72 ms。这说明此例中缓存的树结构和生命周期成本超过了省下的检查成本。

端口错误反例没有任何候选进入结构匹配，完整诊断版本约 **86%** 的时间仍在预过滤；所以其慢不是回溯深度或输出数量导致。以上是隔离诊断，不是产品修改前后的性能承诺。

### 2. 候选收缩在反复构造通用集合

[parents/narrow](../../src/mim/pattern/match.cpp#L478) 对每个已绑定 capture 查找反向 raw-operand 路径，构造/查找祖先集合，再为候选交集生成 Vec、做 rank 查询和排序。根选择会对尚未分配的多个根重复调用这一流程。

此例有 69923 次 `narrow` 调用、263424 次 `parents` 请求。祖先缓存命中率已达 **87.8%**，但命中前仍会复制路径作为 key；`path_to` 的返回值、constraints Vec 和交集结果也有临时对象。这一阶段产生 **147 万次分配、133 MB 累计申请**，是最大的分配来源。缓存命中不等于查询没有成本。

相比之下，portmatching 的 [PGIndexKey::AlongPath](../../../portmatching/src/concrete/portgraph/indexing.rs#L97) 用绑定根、固定端口和路径长度定位后继；固定端口路径返回零或一个节点。这种查询在本次模型中通常无需“祖先集合 + 多集合交集 + 恢复候选顺序”。其约束顺序和所需绑定作用域在 matcher 构造时已确定。

### 3. 通用 continuation 实际进入了堆分配路径

[Continue](../../src/mim/pattern/match.cpp#L64) 是 `std::function<MatchStatus()>`；[operands](../../src/mim/pattern/match.cpp#L152) 每次递归创建捕获当前上下文的 continuation。

这不是仅凭源码推测：原始 Release 二进制的反汇编显示该路径调用 **`operator new(48)`**。诊断中枚举/解释阶段有 **752640 次恰好 48 字节的分配**，占该阶段几乎全部分配；见 [反汇编](results/2026-11-02/profile/operands-disassembly.txt)。同时有 887040 次模式解释访问，其中 69888 次 capture 已经绑定。已绑定 capture 检查身份后仍会继续解释其内部结构。

portmatching 逐模式版本运行预先准备的约束求值器、绑定作用域和端口路径，没有这条按每个 raw operand 构造通用 continuation 的执行路径。这并不说明 trail/backtracking 本身慢；此处测到的是具体解释与内存管理方式的成本。

## 读取集合：在端口 DAG 中是次要成本，在长链中是主因

[on_match](../../src/mim/pattern/match.cpp#L570) 除绑定结果外，还会生成 matched nodes、复制 capture 槽位，并从根和 capture 开始遍历依赖，生成重写验证需要的读取集合。

七模式链中，其输出阶段约占 8%。在临时副本中跳过 matched/read 元数据，仍保留绑定、去重和全部实际匹配检查，搜索从 113.98 ms 变为 **105.32 ms**，因此它不是该例十多倍差距的主要解释。剥离版本仅用于核对映射，不能用于安全重写。

但原生 `pattern_bench` 的单根长链，每个 `q(x)` 都返回一个匹配，每个匹配又重新遍历自己的整个上游前缀：

| 链长 N | 读取遍历弹出次数 | Indexed 输出阶段约占比 |
| ---: | ---: | ---: |
| 80 | 6640 | 69.9% |
| 160 | 26080 | 81.2% |
| 320 | 103360 | 88.6% |
| 640 | 411520 | 93.1% |

该计数在此例恰为 `N*(N+3)`，是 **O(N²)**。每个结果内部会去重，不同结果之间没有共享读取集合的遍历工作。这里的单根匹配判断很便宜，主要时间是在为重写准备结果。占比取每个规模三次诊断运行的中位数。

## 可以据此确定的结论

- 共同 DAG 的主要差距在预过滤缓存、动态集合查询和 continuation 分配；不是 World 重建，也没有证据指向类型等式求解。
- 此例候选已被有效缩小，主要是处理一个候选及维护搜索状态的成本高。
- 单根长链还有独立的读取集合平方复杂度，不能拿“输出只占 8%”推广到所有图。
- MimIR 的端口适配表示更大，进一步放大通用 raw-node 解释和查询成本。不能把上述时间差全部归为算法复杂度差异。
- 对照中最快的是 portmatching naive，所以缺少多模式共享自动机不足以解释当前差距。

本轮只诊断，生产匹配器保持不变，也未对真实 `rule_app` / `graph_rule_app` 的完整重写流水线做耗时分摊。
